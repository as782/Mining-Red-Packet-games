# 矿洞夺宝 v3：一张地图，游戏放在自己的服务上

状态：2026-11-02 定稿；2026-11-06 判定器、游戏站、网页在本机做完，对着开发包的模拟器从头玩到领取结算；同日部署到 Stage（`kddb-staging.lafi.sh`），开了一个 10 🐟 的试玩红包，等真机试玩。生产还没部署。v2（判定器跑整局、一次一张卡）继续服务已经开着的红包。

## 1 为什么改

2026-11-02 实测（生产库，只读）：一次判定从到达到写完，中位数 0.42 秒，最慢的 1% 是 1.3 秒；人多时觉得卡，主要是网页在等自己的结果和动画时把整块牌面停住了，攒下的变化一下子跳出来，再加上换卡。v2 已经改成别人挖开的格子照常显示，但一次一张卡的玩法本身还在制造问题：换卡让“卡片已经更换”的失败和抢格很多；公开数据只有 16 KB，放不下多张卡；每一挖都要排红包站的判定。

用户要的是一次颠覆性的改动：卡片铺成一张地图，游戏放在自己的服务上。

## 2 钱怎么走：一本账

**游戏站记分，红包站只在领取那一下记钱。**

- 游戏站（Worker + Durable Object）记每个人的分。分不是钱：红包站不知道，也不管。
- 每个人只领一次。领的时候，游戏站签一张凭证“这个人在这个红包里一共 N 分”，并把他标成已领（之后不能再挖）；网页把凭证交给判定器（`hb.submit`），判定器验签后 `add: N, settle: true`，红包站当场结算。
- 什么时候领：
  - 玩的人点“见好就收”；
  - 机会用完；
  - 预算分完（见下）：所有人的分都定了，大家一起领；
  - 收尾时间到（截止前 2 分钟）：停止挖掘，页面开着的人自动领。
- **没领的分作废**：红包结束时，没交凭证的人什么都没有，钱照提前结束的规则退给发红包的人。规则说明里写清楚“截止前要领取”。截止前回来，还能领。
- **预算**：游戏站从红包信息读 `pool`，分出去的分加起来不超过它；奖励按剩下的预算封顶（同 v2 按奖池封顶），TNT 扣掉的分回到预算。预算分完，游戏结束。红包站付的时候也按奖池剩余封顶，所以多一层保险。
- 发红包的人自己玩（自领）：他的分领的时候不付款，留在奖池里。

为什么不把分同步给红包站：同步靠玩家的网页，踩了 TNT 马上关掉页面，红包站记的还是踩之前的，到截止照发。只在领取时记一次，就没有这个问题，也不要红包站加新机制。

## 3 凭证和判定器

凭证是一行字（交给判定器的输入最多 200 个字）：

```
kd3.<开放时间毫秒>.<LINUX DO ID>.<分>.<钥匙编号>.<签名>
```

- 签名是 ES256（P-256），对前面几段签，base64url 编码 86 个字；整张凭证约 130 个字。
- 私钥是游戏站 Worker 的 secret；公钥写死在 `judge.js` 里，按钥匙编号查，换钥匙时发判定器新版本，旧钥匙留一段时间。
- 开放时间从红包信息读（`openedAt`，精确到毫秒），判定器拿到的 `submission.hongbao.openedAt` 是同一个时刻：凭证就绑在这个红包上，拿到别的红包用不了。
- 同一张凭证交两次：第一次已经结算，红包站不会再交给判定器。

判定器（第五版协议，不联网，所以领取能一批一起判）只做这些：

1. 拆开凭证，格式不对就回“请在矿洞夺宝里领取”，不加钱。
2. 用 `crypto.subtle.verify` 验签；开放时间等于 `submission.hongbao.openedAt`；ID 等于 `submission.user.id`；分是不小于 0 的整数。
3. `add: 分, settle: true`，回“领取 x”；动态写一句“领走了 x”。
4. 公开数据只写一句概况（几个人领了、领走多少），网页不靠它画。

判定器还要声明参数（第 5 节）：发红包的表单靠它，游戏站从红包信息读它们。`check()` 照旧。

测试：签名测试用的凭证，由作者拿生产私钥对测试里的开放时间签好，写进 `tests.json`（这些开放时间不会是真红包的）；绝不在 `judge.js` 里放一把私钥公开的测试钥匙。`tests.json` 从空的开始，留在 256 KB 以内。

## 5 规则

### 地图

- 卡片放在网格上，每张卡有坐标 `(x, y)`，第一张在 `(0, 0)`。卡的外框 5×5、6×6、7×7 都一样大（360，和 v2 一样“外框尺寸统一”，格子小的卡格子大），放在一个一样大的区块正中（四周比卡宽 16，392 见方），区块之间固定隔 16：卡和卡隔 48。
- **旧卡一直能挖**，所有格都挖开才算挖完（变暗、不能点）。
- **末影珍珠**：在离珍珠所在格最近的那条边外长出一张新卡；那边已有卡就换下一近的边；四边都满，就找离这张卡最近的空位（按格位距离，一样近按右、下、左、上）。珍珠在正中间时也按右、下、左、上。
- 珍珠：5×5 一颗，6×6 随机一到两颗，7×7 两颗（2026-11-06 用户定：地图会分叉，人少也能长出几张卡）。卡上的格挖完以前珍珠总会被挖到，所以地图上总有没挖完的卡。
- **末影之眼和末地宝藏（JP）**（2026-11-06 用户定）：每第 N 张普通卡藏一颗末影之眼（参数“末地宝藏”，默认 3，0 不开；宝藏卡不算张数。判定器第 11 版起参数叫“末影之眼”，只有少 / 正常 / 多三档 = 每 5 / 3 / 2 张，挖到开出的是特殊区块，见 V3_ITEMS.md §14、§17），这张卡的区块一直发紫光，“这张卡还剩”里也有它。挖到眼，在离这张卡至少隔一圈的最近空位开出一张末地宝藏卡：3×3、末地石的格子、区块一直带金光，里面 4 绿宝石、3 钻石、1 金苹果、1 颗**末影水晶**，没有 TNT、珍珠和眼，不再长卡。末影水晶（2026-11-06 用户：大家都去蹲末地石，要有风险，“只是得奖概率更大，但不代表没有风险”）像 TNT，扣还没领的奖励的两倍比例（简单 30%、普通 50%、困难 100%），盾牌照样能挡，望远镜照样能看；手里分少的人值得冲，分多的人去挖反而可能亏。以前开出的宝藏卡（5 绿宝石、3 钻石、1 金苹果）存着的牌不变。2026-11-07 用户：宝藏卡要随机范围的奖励、必有 1～2 颗末影水晶、加双铁镐；水晶可能有两颗，风险大了，钱要多一点，钻石要比绿宝石多：从这天起开的局（局里存 `rules.endMix: 2`），每张宝藏卡依次随机抽末影水晶 1–2、双铁镐 1–2、金苹果 0–1、钻石 3–5（剩下的格子不够就少抽），其余是绿宝石（0–4），平均约 4 颗钻石、1.5 颗绿宝石，约 21 份小奖（以前 19 份），配比由种子和卡号定；以前开的局还是 4 绿宝石、3 钻石、1 金苹果、1 水晶。“这张卡还剩”照常显示这一张的数。没领奖的人都能挖（领了奖本来就不能挖），先到先得，每格照常用一次机会：要不要早领、要不要留几次机会给宝藏，就是取舍。

### 道具（同 v2）

绿宝石、钻石、附魔金苹果（翻倍，有上限参数）、双铁镐（机会 +3）、TNT（扣分，盾牌能挡）、末影珍珠（长出新卡）、盾牌、望远镜（同一张卡上看一个没开的格，一直有效到那格被挖开）。规格、难度、配比沿用 v2 的生成规则。

**道具栏、新格子和区块的完整规则见 [V3_ITEMS.md](V3_ITEMS.md)**（2026-11-10 定下，下面这段是第一步只做工具条时写的，以那一页为准）。

**道具栏**（2026-11-10 用户：道具分主动和被动，被动的可以叠加，望远镜改成主动；先做工具条，只用现有的东西）：从这天起开的局（局里存 `rules.items: 1`）——
- 盾牌最多带 3 面（`SHIELD_CAP`），TNT、末影水晶各用掉一面，带满了再挖到转成一份小奖；
- 望远镜挖到先收进道具栏，不再随机看一格：自己挑一个没挖开、自己还没看过的格子用，看到的照旧只有自己看得见、挖开以前一直记着（`useItem`）；
- 用道具不花机会，也不用等挖掘间隔（道具本来就少）；领了、机会用完、快截止、奖池分完时不能用；只改自己的，不推送、不进动态、不记进逐格记录。

以前开的局照旧：盾牌一面，望远镜挖到就随机看这张卡上的一格。

### 参数

2026-11-06 用户定，只留发红包的人心里有数的五个：

- **预计人数**（1–2000，默认 20）：取代“绿宝石奖励”。绿宝石 = 奖池 × 0.8 ÷（人数 × 每人机会 × 每挖一格平均值几颗绿宝石），至少 0.01；平均值按三种规格的基准配比只数绿宝石和钻石（金苹果翻倍和 TNT 扣回大致抵掉），大约八成奖池能发出去。“怎么玩”里写出算出来的绿宝石和钻石。
- **每人机会**（1–99，默认 20）。
- **难度**（简单 / 普通 / 困难，默认普通）：只管 TNT 多少（5×5/6×6/7×7 各 3/4/6、4/6/8、6/9/12 个）和踩中扣多少（15%、25%、50%），不再联动别的参数。
- **挖掘间隔**（1 / 3 / 10 / 30 秒，默认 1 秒）。
- **末地宝藏**（每几张卡一颗末影之眼，0–20，默认 3）。

拿掉的改成固定的：卡的规格每张随机，道具配比小幅浮动，金苹果一次最多加 10 颗绿宝石，TNT 扣多少并进难度，去掉“连续挖掘等待”（接棒没了）。旧判定器的参数（difficulty、smallReward、tntPercent、appleCap、boardSpec、compositionVariation）写了就照旧用，开着的旧局不受影响。

## 6 网页

用户的描述加上已经定下的（2026-11-02）：

- **平移和吸附**：拖动平移，松手后吸附到最近的一张卡居中；全图那一级不能拖（长出新卡时重新放下所有卡）。
- **区块**：平时看不见。全图那一级所有区块都显示背景和边框；附近那一级指针移到哪块哪块显示；挖卡那一级只有旁边的区块显示，居中正在挖的这块不显示。点区块就切过去。
- **迷雾**：画面四周一圈窄窄的渐隐。
- **聚焦**：居中的卡边框高亮，换卡时边框有过渡动画；道具剩余数量跟着这张卡变，数字有过渡。
- **挖完的卡**变暗，不能点。
- **末影之眼的入场**复用珍珠传送：眼在格子里浮起来、原地转一圈，再拖着金色的尾巴划一道更长的弧线飞到宝藏卡朝着这张卡的那条边，落地是金色的波纹和粒子，宝藏卡翻出来。宝藏卡不闪 NEW，它有 **JP**：还有没挖的格子、又没整张在画面里时，画面边上一直亮着金色的“JP + 箭头”（出现时一道光扫过、呼吸几下，之后静止），点一下飞过去；挖完就没了。动态里写“挖到末影之眼，末地宝藏开了！”。底栏一行（2026-11-06 用户嫌“再长 1 张卡出…”抽象，改成）：下一张新卡里藏着末影之眼 / 往后第几张新卡里藏着末影之眼 / 末影之眼藏在第几张卡里 / 末地宝藏开了，点这里过去（后两种点一下过去）。
- **新卡**（隐性引导，镜头不动，谁挖出来的都一样）：入场是“珍珠传送”——珍珠在挖开的那格亮一下后弹起，拖着紫色的尾巴划弧线飞到新卡朝着旧卡的那条边（约 0.8 秒落地；落在边上，挖卡那一级邻卡露出一截也看得见），落地荡开一圈紫色波纹、溅出几颗像素粒子，新卡外框带一点回弹落定，格子从朝着旧卡的那条边一波一波翻出来；珍珠那格不在画面附近时不飞，只翻出来；减少动画时直接出现。新卡没有整张在画面里时，画面边上闪几下“NEW + 箭头”指着它，然后淡出，点它就移过去；移过去了就不再提醒。
- **三级缩放**（捏合、滚轮）：
  1. 总览：按全部卡算，四周留安全距离；只有一两张卡时不超过第二级；
  2. 附近：固定比例 0.6，画面大就多看到几块；画面小时缩到窄的那边放得下两块多；
  3. 挖卡：画面放得下就是原大（区块之间的距离不随画面大小变），窄的那边放不下一张卡（加两边留白）才缩小。只有这一级能挖。
  点区块（卡上任何地方）就切过去。
- **输入**：滚轮是缩放，一下换一级，放大时朝指针下面那张。浏览器分不清鼠标滚轮和触控板双指滑动，所以触控板双指上下滑也是缩放；平移靠拖动和方向键。触控板捏合、手机双指捏合连续缩放，锁在全图和挖卡两级之间（2026-11-06 用户要求锁死），停下吸到最近的一级。`+`/`-` 缩放；缩放按钮在地图右下角竖着一列，半透明。
- **缩略图**：远处、全图时卡画成缩略图（省性能），但和格子画得一样：没挖的是同样的石头，挖开的是同样的底色和图标，只是没有边框、阴影和“谁挖的”；从格子换成缩略图时看不出来（2026-11-06 用户：全图在手机上突然变成色块很难看）。
- **整张地图一块画布**（2026-11-06 用户：后期地图太大，能不能用 canvas）：远处的卡都画在一块世界坐标里的画布上（MapCanvas），网页里只留近处画格子的、当前卡和刚长出来的卡，盖在画布上面；远处发光的卡（藏着眼的、没挖完的宝藏），光、底色和细边画在另一块不动的画布上（2026-11-07：以前它们一直放在网页里）。卡变了只重画那一块；地图长出画布范围（四周多留 2 格）或全图的清晰度变了（按 √2 一档）才整张重画。全图那一级的区块底色另画一块、只在全图显示；画布上的卡按坐标算点击和悬停（悬停罩一块和区块一样的高亮）。原因是量出来的：几百张卡时每格一个元素、每个图标一张图，有人挖一格或者有东西在动，浏览器每一帧都要把上万个元素重新分层（Layerize），手机上掉到个位数到二十几帧；换成画布后同一张约 570 张卡、20 人在挖的地图，CPU 降速 6 倍下三级都是 57–59 帧，网页元素从约 3.5 万降到几百（2026-11-06 本机 Playwright + Chrome 跟踪）。每张卡一块小画布不够：几百块画布本身也要逐个分层。
- **触屏手势用触摸事件**：use-gesture 的指针事件模式按下记一个、抬起删一个，漏收一次抬起（手指下面的格子正好被换掉）就留下一根“幽灵手指”，单指变双指；触摸事件模式每次按“现在有哪几根手指”重算（2026-11-06 用户：来回捏到全图时偶尔单指变双指）。

## 7 游戏站

- 一个 Worker：沿用 `hbweb-kddb.lafi.sh`。根路径留着 v2 的网页（开着的红包还在用），v3 放在 `/v3/`，接口在 `/v3/api/`。网页和接口同源，不用跨域，令牌的 `aud` 就是这个来源。
- 每个红包一个 Durable Object（`idFromName(红包编号)`，放亚太），存地图、每人的分和机会、预算、动态；用 SQLite 存储，休眠后照样在。
- 接口：
  - `GET /v3/api/state`：整张地图和自己的情况（第一次打开时用，`/hello` 也带着它）；
  - WebSocket `/v3/api/live`：推变化（挖开一格、长出新卡、预算、结束），带序号。带 `v=2` 连的网页收第 2 版：只有变了的那一格（`type: "cell"`，约 200 字节），卡上剩下几个、挖完没有由网页自己算；不带的照旧收整张卡（`type: "dig"`，挖满的 7×7 卡一条约 1.5 KB）。游戏站把推送攒 100 毫秒发一次（2026-11-07 用户定：人多时一秒挖几十格，一格一条推给每个网页，网页几乎每帧都在重画；500 人估计最忙时一秒 65 格）：第 2 版的网页收一个数组（这段时间的几条，按序号），每个网页一秒最多 10 条，别人挖的格子最多晚 0.1 秒出现，自己挖的结果走回答，不受影响；第 1 版的网页照旧一条一条收；
  - `GET /v3/api/since?seq=N`：漏了几条时按序号补：游戏站内存里留着最近 2000 条第 2 版推送，有就给这几条，没有（刚重启、漏得太多）就给整局；
  - `POST /v3/api/dig`：挖一格，回结果（带 `v: 2` 时回答里的 `update` 也是第 2 版）；没挖成时带着那张卡现在的样子（格子被别人先挖了，网页只改这一张）和 `blocked`（为什么不能再挖）；
  - `POST /v3/api/bots`（只在 Stage）：压测机器人挖 `count` 格（最多 500），要带 `X-Bot-Key`（Stage 的 secret `BOT_KEY`；生产没设，接口回 404）。机器人照常走挖一格的规则（机会、间隔、预算），每格挑没挖完的卡上随便一格，名字“机器人 N”，用户编号从 900000000 起；推送和真人挖的一样发给开着的网页（2026-11-07 用户：“有没有超大地图我试试压力”）；
  - `POST /v3/api/use`：用道具（有道具栏的局，现在只有望远镜：`{ item: "spyglass", cardId, index }`），回看到的（`peek`）和自己现在的样子；只改自己的，不推送。没用成时同 `dig`，带着那张卡和 `blocked`；
  - `POST /v3/api/claim`：领取，回凭证；再要一次回同一张。手里没有分时不签（回“手里还没有奖励，不用领取”）。
  - `GET /v3/api/summary`：收益卡：自己的逐格记录（`trail`：挖到什么、加减多少、挖完手里多少、盾牌挡住）、最大一笔、踩雷几次、挡住几次、被炸掉多少，全场领得最多的前 5 名（`top`，每领一个人更新；这一版以前开的局第一次要时从领过的人里算一遍存下）。
- 规则写成纯函数（生成卡、挖一格、放新卡），Worker 和测试共用；随机数用每个红包自己的种子，能重放。
- 红包信息（状态、暂停、参数）30 秒内用上次的；30 秒到 5 分钟先用上次的、后台去读新的，同时要的共用一次；再旧的才等读完（以前每 30 秒那一下正在挖的人都要等红包站）。
- **漏推送不再重读整局**（2026-11-07，生产局 21165916 查出来的）：以前网页序号接不上就 `GET /state` 重读整局，没有“同一时间只读一次”，读回来的整局又可能比推送带来的旧、往回一退又接不上，自己挖的回答比别人那条推送先到也算接不上；挖不成（太快、格子被抢）也重读。那一局 343 张卡、181 人、17 分钟挖了 7149 格，`/state` 被要了 41828 次，送出 1.46 GB（压缩后；游戏站吐出近 12 GB），挖本身只有 10614 次、11.7 MB；那段时间自己的格子要等一次整局读回来才翻开（一秒多）。现在：格子不管先后先放上去，序号接不上的先等 0.4 秒，再按序号补，同一时间只补一次，比手上旧的整局不要，没变的卡沿用原来那一份（不重画）。本机回放：丢一条推送，以前 8 秒重读 172 次、80 MB 停不下来，现在补一次几 KB；推送流量少约六分之五。
- 数据按“红包编号 + LINUX DO ID”存，至少保留到红包结束后核对完。

## 12 部署

本机联调：`cd game && npx wrangler dev --env local --port 8787 --ip 127.0.0.1`，另开 `npm run page`（模拟器 8730，网页 8731）。`game/.dev.vars` 放本地的 `CLAIM_KEY`（单引号原样写 JWK）和 `TICKET_KEY`，不进仓库。`LOCAL_SEED` 让本地开局用固定的种子，按 `game/shared/rules.mjs` 能算出哪格是什么；清掉 `game/.wrangler/state` 重新开局。

构建：`page/frontend` 里 `npm run build`（v2，`dist/`）和 `npm run build:v3`（v3：线上的 `dist-v3/`，开发包的放进 `page/`），再 `node scripts/site.mjs` 拼出 `game/dist/`（v2 在根上，v3 在 `v3/`）。网页里写的是线上红包站的 SDK 地址，SDK 只和加载它的站说话：Worker 发 `/v3/` 时换成这个环境的 `HB_ORIGIN`（`game/worker/page.mjs`），Stage 的网页才接得上 Stage 的红包页。
